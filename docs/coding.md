# 開発と実装の哲学

lub を設計し、実装し、検証するときの判断基準をまとめる。

## 単純さを守る

- Easy より Simple を選ぶ。
    - ある機能をAPIとして提供するとき、1つのAPIに複数の複雑な機能を詰め込むのではなく、1つのことをやるAPIを作り、それを組み立てられるようにする。
    - 引数やオプションなどユーザが使い方を間違えたときは、気を利かせて読み替えたり静かに壊れず、即座にエラーを返却する。
    - `Goっぽさ`
- 実装、ドキュメント、API仕様、ワークフローなど、開発全体を通してDRYを心がける。
    - ある文章を削っても文章の主張に影響がないなら、その文章は不要。
    - 同じ作業に対して複数のやりかたを提供しない。

## 実装に紐づく説明はコードに書く

- 実装に直接紐づく設計意図、前提、制約はドキュメントではなくコードのそばにコメントで書く。
- コメントには「何をしているか」「何を成したか」を言い換えるのではなく、「なぜそうしているか」「前提を壊すと何が起きるか」という意図を残す。

## 書式とコメント

- フォーマッタは各ツールの標準設定をそのまま使い、プロジェクト独自のスタイル規約を作らない。
- コードのコメントは英語で書く。サイトに API リファレンスとして出す XML doc だけは、ドキュメントと同じく日本語で書く。
- コメントは 1 文 1 行を基本にする。

## テスト

- 挙動を足したり変えたりするときは、テストを先に書く。
- テストは stability を重視する。描画やタイミングのように環境でぶれやすい挙動も、CPU ラスタライザ・固定ステップ・出力ハッシュなど決定的な条件で機械的に比較できるようにする。
- 同じコードがすべての実行モード (`tcs VM` / `tcs C` / `.NET`) で同じ結果を出すことをテストで突き合わせる。
- サンプルは実行例であり、テストの代わりにしない。

## 進め方

- 作業はブランチを切って PR にし、テスト・実装・ドキュメントの更新を 1 つの PR にまとめる。マージしてよいかは CI の検査で決める。
- これからやることは GitHub の issue に書き、やったことは PR の本文に書く。リポジトリの中に作業一覧や完了記録は残さない。
