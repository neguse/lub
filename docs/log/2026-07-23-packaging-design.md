# パッケージング設計

> 記録: 2026-07-23 時点の設計。roadmap を「自作ゲーム 4 本の移植と win/web 配信」
> 駆動に切り替えた(PR #15)ことを受けて、配信パッケージの作り方を決めた。
> 現状の記述は同日のコードを読んで確認した挙動で、この文書単体で読めるように書く。
> 同じ議論から派生した言語まわりの案は
> `2026-07-23-language-architecture-notes.md` に分けた。

## 要求

この設計が満たすべき性質。

- R1: 4 本のゲームを win / web のビルド済みパッケージとして配信できる。
- R2: パッケージ生成が CI で再現できる。手動操作やプレイ結果に依存しない。
- R3: `lub game.hxml` で始めた開発が、ビルドシステムや追加ツールチェーンを
  入れずに配信まで到達できる。
- R4: アセットをランタイムが生成できるという lub の設計を損なわない。
  配信のために事前変換専用の仕組みを持ち込まない。
- R5: 自前の main() と任意のネイティブ関数を持つゲームを作る経路が
  win / web の両方に存在する。

## この文書が決めること・決めないこと

決めること: パッケージの構成要素、export の性質、生成キャッシュの規律、
事前生成の宣言主体、ライブラリ化の必要性。

決めないこと(実装時に決める): export コマンドの名前と UI、キャッシュの
キー詳細と保存形式、事前生成フックの API 形状、生成器を player から外す
個別判断、容れ物の形式(zip / 実行ファイル連結)。配信先の実環境検証
(itch.io で WebGPU が動くか)は実装フェーズの最初の作業とする。

## 用語

- パッケージ: 配布物一式。player + snapshot + 生成キャッシュからなる。
- player: ゲームに依存しない lub の実行物。win は exe と同梱ライブラリ、
  web は wasm + js + 静的シェル。lub のリリースとして事前にビルドされる。
- snapshot: あるリビジョンのゲームを動かすのに必要なファイルの閉包。
  生成済み entry Lua、boot / prelude、ゲームデータ。
- 生成キャッシュ: ランタイムの決定的な生成物を「入力のハッシュ + 生成器の
  バージョン」で引ける保存領域。
- 事前生成: export 時に生成器を実行して生成キャッシュへ格納すること。
- export: snapshot と生成キャッシュを作り、player と併せてパッケージに
  固める操作。

## 現状の実体

設計の前提になる、今の lub の挙動。

- 生成 .lua の直パス entry は既にある。`lub path/to/entry.lua` は staging
  なしで任意パスの .lua をロードし、監視は entry ファイルの mtime poll
  だけで Haxe や dev server を要求しない。csproj entry も transpile 後は
  同じ経路に合流する。
- boot と prelude は実ファイル。native は `samples/boot.lua` を cwd 優先、
  無ければ実行ファイル位置からの相対で探す。
  つまり runtime ライブラリの Lua(boot / lub_prelude / lub_io)は
  snapshot に含めるべきファイルで、binary には入っていない。
- serve が web に送っているものは具体的で、初回 SSE は
  「全ゲームデータファイル + 生成済み entry Lua」の中身を 1 つの JSON
  (相対パス → ファイル内容)として流す。HTTP 側はページ本体、
  wasm runtime(lub.js / lub.wasm)、slang-wasm、SSE 接続口を返すだけ。
  つまり snapshot に相当する閉包は serve が既に計算している。
- シェーダのディスクキャッシュは存在しない。native / web とも毎起動
  Slang でコンパイルする。パイプラインキャッシュはあるがメモリ内のみ。
- 決定的な生成物を事前に焼く前例はあるが手動。`web/tcs-prebuilt/`
  (cold 起動 0.5s の正体)と `web/public/haxe-wasm/std-bundle.json` は
  `npm run gen-tcs-prebuilt` / `gen-haxe` で人が再生成する。
- lub は単一の実行物ターゲットで、ライブラリターゲットは無い。

先行例の要点: love2d と usagi はどちらも「事前ビルド済みランタイム +
データ配置、ビルドシステム不要」で配布を成立させている。usagi は
1 コマンド export と、リリースごとに公開する事前ビルド済みランタイムの
取得・検証まで揃えている。ただし両者とも静的データの配布であり、
ランタイム生成には答えを持たない。自前 main() の経路もどちらにも無い。

## 設計

### パッケージ = player + snapshot + 生成キャッシュ

player はゲームに依存しないので、lub のリリースとして一度ビルドされて
いればよい。ゲーム側の産物は Lua とデータだけで、コンパイルすべきものが
無い。だから export はビルドではなく、serve が既に計算している閉包を
snapshot としてディスクに書き出し、player と並べる操作になる。

帰結:

- export に CMake や emsdk を要求しない(R3)。要求した瞬間、エンジンを
  ビルドする都合がゲーム作者全員に転嫁される。
- クロスコンパイルという概念が発生しない。事前ビルド済み player を
  並べるだけなので、Linux 機で win パッケージが作れる(R1, R2)。
- パッケージの起動は「更新が来ない snapshot を読む player」で、dev と
  同じコードパスを通る。golden の byte 一致でパッケージ起動を検査できる
  (検査できるのは golden が踏むフレームの範囲に限る)。
- web パッケージに必要な差分は「SSE を購読する代わりに同じファイルを
  URL から読む」ローダー。native は直パス entry と boot 探索が既にあり、
  残る差分は boot 探索とアセット基準パスの規約化程度。

### 生成キャッシュ — 事前変換の仕組みを作らない

ランタイムが今日やっている生成(transpile、シェーダコンパイル、アトラス
構築など)と別実装の事前変換パイプラインを持つと、二重実装になり
ランタイム生成という強みを自分で削る(R4)。代わりに、ランタイムと同じ
生成器の決定的な出力を生成キャッシュに保存する。

- player は cache hit を読む。miss は、生成器を同梱した player なら
  その場で生成し、同梱しない player では「何が足りないか」を名指しする
  エラーにする。
- 生成キャッシュは、生成器を同梱した player では純粋な最適化、
  同梱しない player では必須データになる。
- 決定的でない生成(乱数が絡むもの等)はキャッシュ対象外。この線引きが
  規律になる。
- luac バイトコード化のような起動高速化も、この枠の一項目として表現できる。
- dev は今日と同じ実行時生成のまま、この保存領域へ write-through する。

### 事前生成はゲームが宣言する

キャッシュに何を入れるべきかの完全なリストは、動的コンテンツがある以上
ゲームにしか作れない。lub ではマニフェストはデータファイルでなくコード
なので、宣言は専用の起動モードで表現する: runtime が生成をすべて記録する
モードで起動し、ゲーム側の専用フックが、使う予定のシェーダやアセット生成を
一通り実行する。

- export はこの起動を自動で行う。プレイ結果に依存しないので CI で
  再現できる(R2)。
- 完全性の責任はゲーム側にある。ツールの仕事は保証ではなく可視化で、
  生成器を同梱しない player での miss を名指しのエラーにする。
  dev セッション中の生成とフックの実行結果との差分報告は将来の可視化案。
- 数フレームの自動実行(golden や headless 検証)はゲーム全体のコード
  パス到達を証明しないので、完全性の検査には使わない。

### シェーダコンパイル

生成キャッシュの代表例。出力は入力に対して決定的で、キーは「slang
ソースのハッシュ、target、entry とオプション、slang / DXC のバージョン」。
SDL_GPU 向けの binding 番号の振り直しのような後処理も生成器の一部として
キーに畳む。

生成器(Slang)を player に同梱するかはターゲットごとの費用対効果で決める:

- native は同梱が自然。今すでにリンクしていて、外す動機がバイナリサイズ
  しかない。同梱していればキャッシュが無くても起動でき、ランタイムで
  シェーダソースを合成する使い方も残る(R4)。
- web は外すのが自然。slang-wasm の同梱は数 MB と起動コストを払う。
  外した場合、シェーダの生成キャッシュは必須データになり、シェーダ集合は
  export 時に閉じる。ランタイム合成を web でやりたいゲームだけ同梱する
  選択も残る。
- win 向け DXIL の事前生成を Linux で行えるかは要検証(DXC の Linux
  ビルドは存在するはずだが、現経路は dxcompiler.dll 前提)。native
  player が生成器を同梱している限り、これができなくても win パッケージは
  正しく動く。初回起動が遅くなるだけで、機能欠損にはならない。

### ライブラリ化 — 自前 main() の経路

自前の main() を書き、任意のネイティブ関数を足したゲーム実行物を作れる
こと(R5)は、lub を CMake のライブラリターゲットとしてリンクする形で
提供する。web で任意のネイティブ拡張ができるのは「ユーザの実行物ごと
emscripten でビルドする」この経路だけでもある。love2d はこの経路を
持たず、エンジンごと再ビルドするしかないのが長年の不満点になっている。

デフォルト経路(R3)にこの層は現れない。この層のパッケージングは各
プロジェクトの管轄で、lub は snapshot の仕様だけ定義する。現状は
単一実行物ターゲットなので、ライブラリ分割という実装を伴う。

## 未決

- 生成キャッシュのキー詳細、保存形式、パッケージへの同梱形式。
- win 向け DXIL 事前生成の Linux 実行(DXC の Linux ビルド検証)。
- 配信先の実環境検証(itch.io の iframe 内で WebGPU が動くか)。
- 生成器を web player から外すかの最終判断(キャッシュ実装後)。

## 次の一歩

lub リポの外のディレクトリに「boot / prelude + 生成済み entry Lua +
アセット」を手で並べて、事前ビルド済み lub がそれだけで起動するかを
確かめる。通らない箇所(boot 探索、package.path、アセット基準パス)が
そのまま snapshot 仕様の最初の項目になる。web 側は初回 SSE の内容を
静的ファイルに展開した版で同じことをやる(購読なしローダーの要否と形が
判明する)。
