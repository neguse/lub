# lub でテトリスを作る作業ログ

## 目的と判定条件

既存の lub を使って、小さな落ち物ゲームを作り、制作中に実際に困った点を記録する。
7 種のミノ、左右移動、回転、自然落下、ソフト・ハードドロップ、ライン消去、
スコア、次のミノ、ゲームオーバー、再開を実装する。
C# の型検査、ゲームルールの自動検査、lub の実行と画像の目視確認で判定する。
成果はサンプルと記録を同じブランチに保存し PR にする。マージは人間が行う。
公開サイトへの追加・配信は今回の対象外。戻す場合はこの変更を revert する。

## 作業中の記録

1. README、CLAUDE、設計方針、ライフサイクル、既存サンプルを読んだ。
   capture / fixed-dt / SpriteBatch / Text が既にあり、エンジンへの機能追加は不要と判断。
2. sandbox の Git は所有者の違いで失敗。コマンド単位の safe.directory で読めた。
   ブランチ作成は .git への書き込み権限で失敗し、通常ユーザーでの実行に切り替えて成功。
   これは lub の機能不足ではなく実行環境の問題。
3. DrawList.cs と Font.cs を名前から推測して読もうとして失敗した。
   rg --files で実在する SpriteBatch.cs / Text.cs を見つけた。推測より一覧確認が速い。
4. samples/29_tetris に自己完結するサンプルを作る方針。
   描画は SpriteBatch、文字は既存の同梱フォントをライセンス付きで複製する。
   ルールは描画から分け、同じコードを自動検査できるようにする。
   今回の検査用シナリオはゲーム側に置く。lub の入力注入機能を先に作らない。
5. 最初の native CLI 起動は NuGet.Config の読み取り権限で失敗した。
   同じコマンドを通常ユーザーで実行すると transpile と D3D12 の初期化まで進んだ。
6. 自分のコードの bag[bagIndex++] に TCS1001 (IncrementAsExpression) 警告が出た。
   添字アクセスとインクリメントを別文にした。共有 Text / MeshText からも
   EnumerateRunes の警告が出ており、自分の変更の診断と既存診断を区別する必要がある。
7. 最初の capture は終了コード 0 だったが、目視すると真っ黒だった。
   生成 Lua は OnInit / OnFrame、lub の契約は on_init / on_frame。
   third_party/tcs は親の指定 b02e66a に対して 9dbe4a0 が checkout されていた。
   当初は別 checkout での回避を考えたが、ユーザーから git submodule update --init の指示。
   実行すると b02e66a に揃った。標準の依存初期化を先に確認すべきだった。
   終了コードと画像ファイルの存在だけでは、ゲームが実行された証拠にならない。
8. submodule を揃えても旧 lub.exe では黒画面のままだった。
   build-release/lub.exe の更新日は 7 月末。標準 build-release.ps1 で再ビルドした。
   その後は指定した 720x720 で初期化され、ゲーム側の実行時エラーが出るようになった。
   バージョン不一致だけが黒画面の原因だったとは断定できない。
9. .NET のルール検査186項目と型検査は成功。しかし Lua 実行では new int[200] の
   未代入要素が nil になり、描画で算術エラー。Reset で全要素を明示的に 0 にした。
   コンパイル成功や .NET テストだけでは実行経路の意味論の差を拾えない。
   この場合も runtime error を繰り返しながら capture は終了コード 0 だった。
10. 0 初期化後、通常画面の描画と 4 ライン消去に成功。
    before.png (frame 5) で下4段と縦穴、clear.png (frame 35) で空の盤面、
    次のミノ、SCORE 832 / LINES 4 を目視確認した。エンジン本体は変更していない。
11. tests/tetris/verify.ps1 にルール検査と CLI シナリオ実行をまとめた。
    終了コードだけに頼らず Lua エラー、期待スコア、撮影通知を検査する。
    ルール検査は native-gate.sh に追加。操作は FixedStep と既存 Input API を利用。

## 振り返り

実際にできたこと:

- C#、SpriteBatch、Text、FixedStep と CLI だけで小さなゲームを作れた。
- 専用エディタ、AI 用プロトコル、外部からの状態取得 API は必要なかった。
- ゲーム側の fixture と Console.WriteLine、既存 capture で回転・即落下・
  ライン消去の結果を画像と数値の両方で確認できた。

手戻りの原因:

| 観測した事実 | 分類 | 次回の対策 |
| --- | --- | --- |
| Git / NuGet のアクセス権で停止 | 実行環境 | sandbox の権限と通常ユーザー実行を区別する |
| 指定外の tcs checkout と古い lub.exe | 依存・実行物 | submodule を確認して標準ビルドを実行する |
| 実在しないファイル名を推測 | エージェントの行動 | rg --files から探す |
| Sized array の未代入要素が Lua で nil | 言語間の意味論 | 実際の Lua 経路で動かす。今回は明示初期化 |
| runtime error があっても capture は exit 0 | 成否の報告 | ログと期待値も検査する |

今回の結果から優先したい改善:

1. 依存の指定コミットと実行物の情報をまとめて確認できる起動前診断。
2. 検証実行時に callback 不在や Lua エラーを非ゼロ終了にする選択肢。
3. エラーを生成 Lua の行だけでなく元の C# の場所へ結びつける診断。

この3点は今回の失敗から出た候補で、実装した機能ではない。
前の会話で挙げた汎用 pause / step / inspect 窓口が最優先だという根拠は、
この実験からは得られなかった。シナリオはゲーム側で短く書けた。

評価の限界:

- 1本の小さなゲーム、Windows D3D12 での実験に限る。
- 自動シナリオはゲームメソッドを呼ぶ。OS のキー入力や操作感を試した証拠ではない。
- ホットリロードの反映時間、Web 実行、音声、実プレイヤーによる面白さは測っていない。
- .NET 単独検査はルールを確認したもの。Lua 実行で同じ意味になるとは限らず、
  実際に今回1件の差を見つけた。
- IncrementAsExpression の警告は指定外の tcs で観測した。指定バージョン固有の
  制約として一般化しない。
