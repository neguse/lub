# プロダクト設計

## 目的

lub は、試行錯誤の摩擦を極限までなくし、作り手が細部までこだわりきるためのコード中心のゲームエンジン。

## 体験の柱

### コード中心でゲームを組み立てる

エンジンの機能をすべてプログラマブルにする。
ゲームに必要なデータ構造や制作の流れを、作り手自身がコードとして組めるようにする。

### 変更を速やかに試せる

C# のサブセット (TinyC#) と専用エディタ (lider) により、ゲームを動かしたままコードや素材を書き換えて即座に反映し、その場で状態を見て比べられる。
状態のスナップショットを保存・復元することで、時間や状態を行き来しながら変更したコードを比較・動作確認できる。

### 1 つのコードでどこでも同じように動く

同じゲームコードが Windows / macOS / Linux / iOS / Android / Web で動く。
普段の試行錯誤はホットリロード (`tcs VM`)、配布時は事前コンパイルで高速処理 (`tcs C`)、深い調査には `.NET` と、同じソースのまま 3 つの実行モード (exec mode) を使い分けられる。
また、ゲームの論理を支える数値計算 (単精度浮動小数と超越関数) は OS や実行モードをまたいで同じ結果を返す。

### モダンな 3D ゲーム体験を構築できる

compute shaderやstorage bufferを含めたrendering pipelineをプログラムで組める。

## API 設計

lub の API は、基本となる `Lub API` と、典型的な実装パターンをまとめた `Lubx API` の 2 層で提供する。

Easy より Simple を選ぶ。
書きやすさのための近道や暗黙の振る舞いを増やすより、小さく少ない部品で動きが予測できることを優先する。

### immediate なモデル

描画や物理のリソースは毎フレーム宣言する immediate な形をとり、エンジン側に隠れた状態を持たないことで、ホットリロードと組み合わせて破綻しにくくする。

### `Lub API` — 最小限の土台

`Lub API` には、エンジン自身が持たなければ一貫性を守れない最小限の機能だけを置く。

- 実行の境界: 起動、終了、フレーム進行、時間刻み
- 外部状態の読み取り: 入力や環境状態をフレーム内で一貫して読む仕組み
- リソースの識別と寿命: 名前と版による管理、ホットリロードをまたぐ整合性
- プラットフォーム差の吸収: OS や GPU の違いを上位へ漏らさないコマンド面
- 診断: ログ、画面キャプチャ、内部状態の観測など、人のデバッグと自動検証の両方に要る口

ゲームのルール、画面遷移、アセット制作の流れ、既存エンジン向けの互換層、書きやすさのためだけの短縮呼び出しは `Lub API` に入れない。
同じ処理が複数箇所で必要になっても、それだけでは `Lub API` に足さない。

### `Lubx API` — 書き換えられる便利層

2D / 3D の描画補助、カメラ、アセット読み込みなど、よく使う実装パターンは `Lub API` の上に C# で書いた `Lubx API` として提供する。
エンジン本体に閉じ込めず、利用者がコードを読んで必要に応じてホットリロードで書き換えられる形にする。
既存の C ライブラリが要る処理 (音声デコードなど) だけは、`Lub API` とは分けた `Lubx API` の面から内部実装を呼ぶ。

## やらないこと

- 組み込みの GUI エディタやエンジン独自のアセット形式
    - 全てをプログラマブルにしコード中心の開発体験を提供するという目的と衝突するため
- 大量オブジェクトや巨大シーンをさばく極限の実行性能追求
    - マルチスレッドやECSといった、ゲーム側の開発方法を制限してでも性能を上げるための機能は当面はやらない
    - ホットリロードによるイテレーション速度を追求するという目的と衝突するため
    - リリース時のビルドでは他のゲームエンジンと比べてもそこまで見劣りしないか、むしろゲームごとの最適化次第では勝ちうる見込み
- AI ベース開発にしか役に立たない機能
    - MCPなど (CLIやAPIとしての連携手段は提供しうる)
- OpenGL / WebGL へのフォールバック
    - 当面はコンピュートやストレージバッファを前提とする
    - 将来的には、より低スペックなハードウェア (Playdate や Raspberry Pi Zero 2 など) をサポートしうる
